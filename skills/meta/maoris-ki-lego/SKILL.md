# Maoris KI-Lego — сборка готовых решений

Подобрать минимальную достаточную сборку под любой результат пользователя и выполнить поручение в текущем чате. Область применения открытая: отсутствие готового примера означает собрать новый маршрут, а не отказать или свести запрос к знакомой категории.

## 1. Понять задачу и выбрать глубину

Определить результат, аудиторию, ограничения, исходные данные и критерий готовности. Контекст: NS Reinigungsdienst, Maoris Digital Lab или иной/общий проект; сохранять границы данных. Продолжение той же задачи выполнять с уже выбранной сборкой; пересматривать только изменившиеся требования, доступ или источники.

Прочитать [правила совместимости и продолжения работы](references/operations.md). Если задача ясна и есть достаточные данные/инструменты — быстрый подбор: один подход, необходимые инструкции и сразу работа. Для новой интеграции, спорного решения, существенного риска или нехватки возможностей — углублённый подбор. Простой перевод, приветствие и короткое уточнение выполнять напрямую.

## 2. Найти минимальную достаточную сборку

Сопоставить доступные встроенные возможности, установленные скиллы, материалы KI-Lego и подключённые плагины. Прочитать инструкции выбранных скиллов. Не устанавливать новый компонент, если доступного достаточно.

Проверить актуальные AGENTS.md и нужные материалы https://github.com/Demik-777/maoris-ki-lego по [порядку поиска и версий](references/discovery.md). Изучать все названия/описания индекса, а полный текст — только выбранных материалов и зависимостей. [Маршруты](references/assembly.md) читать при необходимости: это открытые примеры, не обязательная классификация.

При нехватке возможности сначала проверить доступный поиск плагинов, затем готовые шаблоны, библиотеки и официальные источники. Искать по недостающей возможности, не по всему запросу. Проверить фактический доступ; если подключения нет, продолжать независимую часть. Не просить прислать данные, пока подходящий подключённый источник не проверен.

## 3. Выбрать и коротко объяснить

Оценивать кандидатов по соответствию результату, фактической доступности, качеству доказательств, затратам, совместимости с текущим стеком и поддерживаемости. Предпочитать существующий простой путь; дополнительные зависимости обосновывать пользой. Неподтверждённые цену, доступ и совместимость обозначать неизвестными.

Выбрать обычно 1–3 основных компонента плюс необходимые зависимости; это ориентир, не квота или предел. Дать один рекомендуемый путь. Альтернативы добавлять только при существенном компромиссе. AGENTS.md, Council, AutoGen и другие внешние проекты рассматривать по условиям задачи; не проверять каждый фреймворк для каждого запроса.

Для простой сборки хватит 1–3 предложений: результат → средство и польза → выполнение. Для сложной дать компактную таблицу «компонент / конкретная польза / статус». Называть инструкции прочитанными, сервис доступным и действие выполненным только по фактическому подтверждению.

## 4. Выполнить и проверить

Если поручено создать — создать результат, а не только план или список инструментов. Если поручено оценить/подобрать — завершить этим результатом. Для обратимых решений действовать без лишнего согласования; задавать только вопросы, от ответа на которые зависит результат. Не выполнять внешние действия сверх поручения и правил среды.

Проверять результат по критерию готовности: существенный сценарий программы, данные/расчёты, визуальный рендер или факты и язык текста. Для новых изменяемых фактов и технологий читать актуальные надёжные источники. Официальные рекомендации OpenAI применять к соответствующим возможностям; не называть все наши внутренние правила стандартом OpenAI.

Не выдавать методику одной модели, описание роли или макет за реальный запуск нескольких моделей, инструмента или интеграции. Не запускать агентов, платные API, установку или публикацию из одного упоминания в каталоге.

## 5. Сохранить возможность продолжения

Для многошагового проекта сохранить рядом с его материалами краткое состояние по [operations.md](references/operations.md): результат, выбранная сборка, решения, проверки, оставшиеся задачи и следующий шаг. Для обычного ответа отдельный файл не нужен. Использовать существующие правила хранения; не создавать второй архив проекта. В финале кратко сообщить созданное, проверку и существенные ограничения.

## Применение и версия

Автоматический выбор разрешён там, где скилл доступен модели; межчатовую память и срабатывание в каждом интерфейсе он не гарантирует. При явном вызове применять его к текущей задаче. Проверять установленный выпуск по references/source.json и scripts/verify_release.py. Основная редактируемая версия и порядок обновления описаны в operations.md. Недоступный источник обозначать честно и продолжать доступную часть.
